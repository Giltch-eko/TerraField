# Satellite map and plant catalogue — implementation and data notes

## Audit and scope
The supplied project is static HTML/CSS/JS served by a Node 24 HTTP API. SQLite held reports and soil cache. The existing `engine.js` scores 21 documented ECOCROP crop profiles with rules; it is **not an ML model**. Before this enhancement `/api/plants` returned 2,302 historical ECOCROP records as one JSON file, and the browser filtered them. There was no interactive satellite map. The user's new reference screenshot was not attached. Existing project screens and behaviour were preserved; the field map now sits only on the Global Soil Data page (updated by user request).

## Satellite map
Leaflet 1.9.4 is locally bundled under its BSD-2-Clause license (`client/vendor/leaflet/LICENSE`). Its map loads tiles directly in the browser from **EOX Sentinel-2 cloudless 2016** (modified Copernicus Sentinel data 2016 & 2017). EOX's 2016 layer is CC BY 4.0; attribution and links appear on the map. The public EOX endpoint requires no API key, offers no SLA, and requires reasonable use. Source: [EOX licensing and endpoint FAQ](https://cloudless.eox.at/documentation/faq) and [EOX attribution](https://eox.at/2024/08/sentinel-2-cloudless-2023/). Do not prefetch, scrape or redistribute tiles as a standalone dataset. Tiles are requested only as the user views/pans the map. The viewport is disclosed to the provider when tiles are requested; see its privacy/usage terms.

The roughly 10-metre, multi-date 2016/17 composite is **not live**. It does not guarantee visibility of small field boundaries, roads, individual crops or field health. Zoom beyond native resolution enlarges pixels rather than adding detail. The default is an illustrative area in Andhra Pradesh, not the user's field. No automatic boundaries or sensor readings are implied.

Search above the map uses the existing server-side `/api/location/search` adapter for explicitly submitted queries (no autocomplete). Choose a result to fly to an approximate reference point; countries/regions use a wider zoom than cities/features. Search results may be approximate or ambiguous. Click the actual field or enter coordinates after finding the area. Names and addresses are sent to the services described in [GLOBAL_MAP_SEARCH.md](GLOBAL_MAP_SEARCH.md); ordinary map tiles also disclose the viewed area to EOX.

Pan, zoom, reset, point selection and user-drawn polygons are supported. Enter coordinates to navigate; latitude ±90 and longitude ±180 are valid, but the Web Mercator map cannot display beyond ±85.05112878°, so a polar marker is drawn at the visual limit with a warning, while the exact coordinate is retained. Polygon vertices are actual geographic coordinates, not pixels. Draw by clicking or by entering each vertex, then finish; drag vertices to edit, finish or cancel. Keyboard users can draw using the coordinate entry, but dragging an existing vertex requires a pointer; redraw with coordinates as an alternative. User-drawn outlines are **not legal boundaries**.

Polygon area uses a spherical approximation and is shown in hectares and acres. The local projected area-weighted centroid is used only if its six-decimal coordinate is strictly inside the ring; otherwise an interior scanline point is chosen. This is a field-scale approximation, not geodesic surveying. Degenerate, self-crossing, antimeridian-crossing, polar or >1°-wide/high rings and rings with more than 100 vertices are rejected. Verify the location before using it for soil lookup. Area is not a survey.

Point or finished polygon coordinates transfer to the crop profile when the user chooses **Use this field in New Analysis**, or applies matching soil data. When the coordinate changes, prior SoilGrids pH/texture and current modelled weather are cleared instead of attributed to the new point. Manual and illustrative inputs are retained with a prominent verification warning; not all manually entered values can be automatically tied to a source. Profile reset and loading an example clear the map selection. Coordinates and finished geographic polygon are retained in browser session storage until cleared or the browser-tab session ends; crop and dates are only in memory. New reports retain a matching validated polygon, approximate area, source and representative-point method; older reports may lack these. For shared devices clear the selection. Soil lookup is optional and its estimates are not field tests. See [GLOBAL_MAP_SEARCH.md](GLOBAL_MAP_SEARCH.md) for full limitations, providers and tests.

## Database and API
On startup, additive schema creation and a one-time `catalogue_migrations` seed populate the existing database. Existing `reports`/`soil_cache` are not deleted. Back up the SQLite database **and browser workspace key** before upgrading. Initial startup takes longer while building the catalogue index. Tables:

- `catalogue_plants`: source record id, original scientific/display names, normalized exact-name key (unique), source URL, dataset licence, weed flag, optional linked scored-crop id, full source JSON and update timestamp.
- `catalogue_tags`: normalized relation for category, type, use and region filters; indexed on `(kind,value,plant_id)`.
- `catalogue_search`: SQLite FTS5 trigram index over names, synonyms, categories, types and uses. Searches of one or two characters fall back to a parameterized scan; three or more use the index.
- `catalogue_migrations`: records the one-time ECOCROP seed.

`GET /api/catalogue?q=...&page=1&category=...&type=...&use=...&region=...&screened=yes&weeds=include` returns up to 24 records, matching and overall counts, page count and a caveat. Defaults hide records the source also labels weeds. `GET /api/catalogue/filters` returns filter choices. `GET /api/catalogue/{id}` returns one record; `GET /api/catalogue-crop/{cropId}` looks up a source-linked scored crop. These are unauthenticated public reference endpoints. `/api/plants` is retained for old clients and still returns the original static file; new catalogue pages do not use it. See [API.md](API.md) for status codes and examples.

The displayed **2,302** count means distinct historical source records by normalized exact scientific-name string. It is not a claim that 2,302 names have independently verified current taxonomy, that each plant is cultivated in India, or that they represent 2,302 species: some are infraspecific taxa, and synonym/accepted-name reconciliation is not complete. Records retain ECOCROP source IDs, source URLs, licence and documented use evidence. Unknown family, accepted name, cultivar, region and cultivation facts remain unknown; no plant images are supplied.

### Provenance and the 20,000 target
Included records: FAO ECOCROP, adapted from the pinned [OpenCLIM mirror](https://github.com/OpenCLIM/ecocrop) and [EcoCrop-ScrapeR use table](https://github.com/supersistence/EcoCrop-ScrapeR), with provenance and hashes in [DATA_SOURCES.md](DATA_SOURCES.md). FAO catalogue identifies ECOCROP as CC BY 4.0. Uses and names are historical; source use data are not a modern independent verification.

Investigated but **not imported**: [GBIF Backbone](https://www.gbif.org/dataset/d7dddbf4-2cf0-4f39-9b2a-bb099caae36c) (CC BY 4.0) and [World Flora Online backbone](https://www.worldfloraonline.org/downloadData) (CC0) provide taxonomic names, not proof of human use/cultivation; blindly adding wild taxa would misrepresent the requested catalogue. [Kew](https://www.kew.org/science/collections-and-resources/data-and-digital/terms-of-use) applies dataset-specific licences and some use/image content has additional restrictions. [USDA GRIN](https://npgsweb.ars-grin.gov/gringlobal/taxon/taxonomydetail?id=461441) has economic-use records and is a candidate, but an appropriately licensed bulk extract, stable data schema, source-level permissions and reliable deduplication/matching were not established here. No Kew, GBIF, WFO or USDA data is represented as imported. The target is short by **17,698 records** relative to the 20,000 *record count*, and the number of fully verified cultivated taxa is not established.

### Repeatable import
The offline CLI processes newline-delimited JSON in batches of 250, with per-record savepoints, existing-ID skip, exact normalized scientific-name collision detection and error reporting. It does not scrape data and cannot itself verify the truth or legal rights of submitted records. The operator must obtain permission and evidence, review taxonomy and prepare one JSON object per line. Include `id`, `name`, `scientific_name`, `source_url` (HTTPS), `license` and arrays for `uses`, `aliases`, `synonyms`, `life_forms`, `categories`, `purposes` and optional `cultivation_regions`; preserve source ids, licensed citations, rank and true nulls. Fields not known should be omitted/null rather than invented. `screened_crop_id` should only be supplied for a verified explicit relationship. Test on a copy first:

```sh
# Stop the server and back up the SQLite database and browser workspace key first.
# Start the server once to initialise an existing DB, or set DATABASE_PATH explicitly.
DATABASE_PATH=server/terra.db node tools/import-catalogue.js reviewed-records.ndjson
```

On Windows PowerShell: `$env:DATABASE_PATH='server/terra.db'; node tools/import-catalogue.js reviewed-records.ndjson`. Exit 0 means all lines were accepted; 2 means one or more records were rejected or collided; 1 means fatal failure. Batch commits mean earlier batches remain after a fatal failure. Re-running skips existing source IDs without overwriting them; inspect skipped counts and review updates manually. Conflicting names under different IDs are reported for manual review, not merged. This is an exact normalized-name duplicate check; it does **not** resolve synonyms, different spellings or taxonomic changes. Back up before importing; do not run untrusted imports on a production database.

The scorer is unchanged. Only explicit ECOCROP source links connect its 21 crop classes to catalogue records; unknown links return 404. More supported crops would require sourced environmental profiles, a specified scoring method and independent validation; do not assume all library records can be recommended or claim improved predictive accuracy.

## Verification
See [TESTING.md](TESTING.md) and `tests/last_enhanced_browser_run.txt`. Tile loading was observed with HTTP 200 in Chromium on 2026-10-30. Availability can change. Map point/outline/area, zoom, pan, reset, failure messaging, profile/report link, database-backed pagination/search/filter/detail, screen widths and existing recommendation flow were exercised. A 20,000-row **synthetic, disposable in-memory benchmark** tested indexing and pagination; those test rows are not bundled data. No public deployment or native-device testing was performed.
