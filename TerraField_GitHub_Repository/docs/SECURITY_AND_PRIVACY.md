# Security and privacy

## Existing controls and gaps
- Report and plan routes derive an owner hash from a random browser-held 64-hex bearer key. A different valid key gets a 404 for report IDs; missing or malformed key gets 401. Keys are stored in localStorage and sent in a request header; any script with same-origin access or anyone with the key can use it. No login, identity proof, password reset, session rotation, recovery, MFA, server-side revocation or account management. Losing browser storage loses access. This mechanism is not production authentication.
- SQLite queries use parameters; server validates profiles, field geometry, content types and body size, recomputes ranking/area and scopes reports/plan by owner. Browser output uses HTML escaping, restrictive same-origin CSP (with EOX image allowance), safe JSON errors, `nosniff`, and CSV formula-prefix mitigation. No comprehensive penetration test, third-party code review, formal accessibility review, security headers/cookie policy analysis or production-grade abuse protection was performed. CSV mitigation cannot guarantee safety in every spreadsheet; treat exports as sensitive and inspect before opening.
- User-entered locations, field polygon, profile, source labels and plan live unencrypted in SQLite and may also be stored in browser memory/sessionStorage/localStorage. Some may be sensitive. Do not use a shared browser for confidential information. Anyone with DB or backup access can read it; the owner hash is not encryption.
- Place queries and precise coordinates can be sent to external Photon/Open-Meteo/ISRIC/EOX services, depending on features used. Each has its own privacy, fair-use and licensing rules. Read them and obtain informed consent before real-world use. Avoid logging query strings (server logger strips them), but IP addresses and request paths are logged.
- TLS, actual authentication, authorization lifecycle, retention/deletion policy, consent, privacy notice, audit/security monitoring, rate limiting, provider-specific API limits and reliable offsite encrypted backups must be designed and independently tested before public deployment. No secrets are required for current APIs; do not put future API keys in frontend code. Never commit `.env`, database files, backup copies or browser keys. `.env.example` is documentation; the server does not automatically load it.
